# Apple HIG 界面文案写作

把 Apple HIG《Writing》落成可执行的写作与评审流程：先定 voice，再按情境调 tone，最后逐屏收敛到清晰、一致、可操作。

唯一判断标准：**这句话是否帮助用户更顺地完成他想做的事。** 做不到就删掉或改写。

## 适用与不适用

- 适用：按钮、链接、标签、占位符、提示、报错、空状态、通知、设置说明、无障碍描述；也可用于定 voice、建术语表、查跨屏措辞一致性。
- 不适用：视觉排版、动效、组件形态选择（属 HIG 设计与组件章节）。

## 工作流

### 1. 确认 voice

先问清「对谁说话、希望用户有什么感受」。用户熟悉什么词？期望情绪是什么（银行 → 信任稳定；游戏 → 兴奋有趣）？项目已有术语表就先读取复用，不要另起一套。

### 2. 按情境定 tone

voice 不变，tone 随情境变。写每条文案前判断：用户此刻在现实世界做什么、在 App 内处于什么状态（成功 / 失败 / 等待 / 困惑）。严肃情境（支付失败、检测到摔倒）用直接克制的措辞；正面成就（达成目标）可以轻松祝贺。**不要用同一种 tone 覆盖所有场景。**

### 3. 逐屏落笔

- 每屏最重要信息放最前，注意元素顺序。
- 用分行、留白让文字易读。
- 一屏多个概念就拆屏，并设计跨屏信息流。
- 逐词自检：这个词必须存在吗？能更少吗？**朗读出声**验证。

### 4. 统一语言模式

1. **按钮与链接**：按钮用动词（「发送」优于「就这么办吧」）；链接用描述性短语（「了解 UX 写作」优于「点这里」）——读屏用户会脱离上下文单独听链接文本。
2. **多步骤流程**：起点用「开始使用」，推进词在「继续」「下一步」中只选一种并全程贯彻，结束用「完成」。
3. **大小写**：按 UI 元素类型各定一种并全应用统一（如所有弹窗标题用 Title Case、所有大标题用 sentence case）。中文界面主要体现为标点与空格规范，两者也要全应用一致。
4. **物主代词与视角**：「收藏」优于「你的收藏」；若使用就不得切换视角；**彻底避免「我们」**——「无法加载内容。」优于「我们加载内容时遇到问题」。

### 5. 特殊场景（最容易写坏，逐项处理）

- **空状态**：欢迎 + 说明为何为空 + 引导可执行动作（按钮或链接）；不放关键信息，空状态是临时的。
- **错误信息**：就近展示、不指责、明确告知如何修复；不用「哎呀」「糟糕」这类感叹词，不写「名称无效」这类零信息文案。若问题改文案解决不了且影响面大，直接提出改交互。
- **设置项**：标签直白实用；需要解释时**只描述开启时的行为**（关闭状态可自行推断）；指路必须给直达链接或按钮，不要用文字描述位置。
- **输入框**：标签清晰 + 占位符给格式示例（`name@example.com`）；错误就地展示且是指导性措辞（「姓名只能使用字母」优于「不要使用数字或符号」）。
- **消息投递**：先评估紧急度、用户看到时的场景、所需辅助信息量，再在通知 / 弹窗 / 动作表之间选择，并使用匹配情境的 tone。

### 6. 按设备适配

措辞跨设备一致，长短与视角可调：手势动词必须匹配设备（触屏「轻点」、桌面「点击」，不混用）；小屏（手机 / 手表）必须简短；电视常处公共空间、观看距离远，注意「对谁说话」且同样简短。

### 7. 交付前自检

逐条过《评审清单》：信息、动作、一致性、设备、特殊场景、投放六个维度，任一为「否」即需修改。

## 输出规范

- 改写时给**原文 → 改写 → 理由**三段式，理由必须指向上面某条具体规则，不要只说「这样更好」。
- 只改文案，不擅自改代码结构、组件形态或交互逻辑；文案修不了的问题单独指出并说明原因。
- 专有术语优先沿用项目既有术语表；没有时才建议新建，并提醒用户确认。
